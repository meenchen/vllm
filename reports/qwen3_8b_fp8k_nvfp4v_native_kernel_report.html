128 bytes

64 bytes
V scales

Per head-token at head dimension 128: 200 bytes total. The physical page layout stores all K data, then V data, then V scales. The cache is a single allocation with logical strided views, not a BF16 shadow.

Implementation

Native XQA decode

  • Extends FlashInfer XQA with independent compile-time K and V cache types.
  • Uses E4M3 K, packed E2M1 V, and one E4M3 scale per 16 V elements.
  • Passes independent K/V data strides, scale strides, and global scales.
  • Supports BF16/FP16 queries, head dimension 128, and GQA ratios 1/2/4/8/16.
  • Reuses XQA online softmax, paging, multi-CTA reduction, and sink support.
  • Uses packed FP8/FP4-to-FP16 conversion followed by vector BF16 conversion.

vLLM integration

  • Wraps XQA in an opaque custom op with declared output/workspace mutations.
  • Preallocates rank-wide workspace and semaphores before graph capture.
  • Contains no CPU polling, host synchronization, or forward-time allocation.
  • Native decode is opt-in via VLLM_FP8_K_NVFP4_V_NATIVE_DECODE=1.
  • Unsupported shapes and prefill use the same packed-cache Triton fallback.

Packaged Cubin

TensorRT-LLM source

  • Builds a public CUDA XQA specialization for E4M3 K and E2M1 V.
  • Targets SM100a, BF16 query/output, head dimension 128, GQA ratio 4, and page size 16.
  • Produces a 124,664-byte cubin with SHA-256 1250d87f...e70.
  • Direct CUDA-driver validation matches the reference with zero maximum absolute error.
  • This is an XQA cubin, not a new proprietary TRTLLM-GEN tensor-core specialization.

FlashInfer distribution

  • Ships the cubin in the wheel and verifies its full SHA-256 before loading.
  • Caches the module and function per CUDA context; decode launches do not poll or synchronize the CPU.
  • Uses a thin CUDA-driver launcher compatible with torch.compile and CUDA graph capture.
  • Selects the cubin only for the exact specialization; other shapes retain source XQA.
  • Registers the launcher for FlashInfer AOT/JIT-cache wheel generation.

The tested source wheel still JIT-compiles the thin Python/CUDA binding. Packaged and source-XQA wrapper builds took 9.5 and 8.3 seconds, respectively, and full server startup was dominated by model and Python initialization. A prebuilt flashinfer-jit-cache wheel is required to remove wrapper compilation entirely.
